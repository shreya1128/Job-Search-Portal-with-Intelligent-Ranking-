# Phase 7 - the Flask web application (Stages 1 and 2 of 5 built)

Written 2026-10-13. Governing document: the user's "MASTER PRODUCT DIRECTION" (2026-10-11). Phase 7 is being built in small stages, each reviewed before the next. **Stage 1 (design system, public pages, Find Jobs, Job Details) and Stage 2 (Saved Jobs, Profile, account settings, workspace) are built and verified. Stages 3-5 are not started.** Nothing here is claimed to be production-ready.

## 1. What a visitor can do today

Navigation, exactly as the product direction specifies and in this order: **Home | Find Jobs | Recommendations | Resume | Career Insights | Saved Jobs | Profile** (no IR or DL experiment pages in the navigation; the algorithms stay inside the product).

| Page | Address | State |
|---|---|---|
| Home | `/` | Built. Headline, one search box, six job areas with real counts, three example postings, a closing row. Deliberately short (the first version put everything on one page and the user called it cluttered). |
| Find Jobs | `/jobs` | Built. Plain-language search, location (city or country), filters (job area, country, experience band, employment type, required skills, title words, more), sort (best match / experience low-high), ten results per page, one-sentence "why it matched", skill chips, active-filter chips, empty/error states. `/search` redirects here (301). |
| Job Details | `/job/<id>` | Built. Facts, skills, description with the query words highlighted, "Why it may suit you" (only from a saved profile or an analysed resume), related jobs, apply link **only when the data has a safe http(s) link**, fraud-flag banner. |
| Log in / Create account | `/login`, `/register` | Built and tested (see section 6). |
| Saved Jobs | `/saved` | **Stage 2, built.** The jobs the user saved, most recent activity first, 10 per page, filter "all / not marked as applied / marked as applied". Each card: title, employer (never a generated placeholder name), city, stated experience, last activity date, the skills of the posting (the ones also in the user's profile are highlighted), **Mark as applied / Remove applied mark** and **Remove from saved** (POST + CSRF, return only to a page on this site). The page says "Applied" is a mark the user sets: Jobintel cannot see employer replies, so it tracks no other status. Login required. |
| Profile | `/profile` | **Stage 2, built.** One form: name, highest education, short summary, target role, one preferred location, years of experience (0 is a real answer, blank is unknown), skills (comma separated; only names in the skill table are stored, the rest are listed after saving). A checklist of what is filled in (explicitly "not a score") and a "Not stored yet" note. The old workspace form address `/dashboard/profile` still works (POST). Saving never touches the resume fields. Login required. |
| Account settings | `/account` | **Stage 2, built.** Account facts, change password (current password required), download my data (`/account/export`, JSON of everything stored about the user), delete my account (password + a tick; deletes every row linked to the user, leaves job postings alone). No e-mail change and no password reset by e-mail (Jobintel sends no e-mail). Reached from the user menu; not in the navigation. |
| My workspace | `/dashboard` | **Leaner in Stage 2.** Counts of real activity (viewed / saved / marked as applied), profile checklist, resume status, last five saved, marked-as-applied, recently viewed, recent searches, and a note that recommendations and skill gaps appear when those pages are built. A new account shows empty states, nothing invented. Login required. |
| About, Privacy, Terms, System status | `/about`, `/privacy`, `/terms`, `/health` | Built. **Privacy and Terms are drafts** with a visible notice; the user must review them before any public use. Status shows part names only; the reasons are shown only when `JOBINTEL_DEBUG=1`. |
| Recommendations, Resume, Career Insights, Skill gap | `/recommendations`, `/resume`, `/career-insights`, `/skill-gap` | **Placeholders** ("Not built yet", with what the page will do and which stage builds it). They show no invented content. |
| Errors | any bad address | Designed 404 / error pages with no stack trace or paths. |

JSON endpoints kept (the web UI no longer uses all of them): `/api/search`, `/api/skills`, `/api/health`, `/api/interact` (POST, login + CSRF), `/api/job/<id>/function`.

## 2. Design system (`jobintel/web/static/css/app.css`)

* Near-black warm charcoal page (`#121110`), warm-white text, muted-grey secondary text, one restrained amber accent (`#d9a441`), sage for "you have this", muted brick for "missing", thin borders. No gradients, glow, sparkles, particles or purple.
* Bootstrap 5.3.3 (vendored, dark mode) with the tokens overridden. Fonts self-hosted (OFL): Fraunces (headings), Atkinson Hyperlegible Next (body). Nothing is loaded from a CDN; the Content-Security-Policy is `default-src 'self'` with `script-src 'self'`.
* Responsive: the navigation becomes a drawer below 1200 px; verified at 390, 820 and 1366 px.
* Accessibility: skip link, visible focus ring, labels on every field, `aria-current` on the current page and pagination page, live region for messages, reduced-motion respected, whole job card is one link. Measured contrast (WCAG): body 16.5:1, muted 7.4:1 (5.9:1 on raised surfaces), faint/placeholder 5.1:1, link 10.3:1, amber button text 8.15:1, chips 5.9-9.1:1, form-field borders 3.2-3.5:1 (needs 3:1). `tools/phase7_scratch/contrast.py` recomputes all of it.

## 3. Honesty decisions (these bound what the UI may say)

Each follows from a measured fact about the data (43,869 jobs in the database; 42,075 searchable documents from three datasets: EMSCAD 16,204, LinkedIn 13,989, Naukri 11,948):

* **No salary sort, filter or salary analytics.** Salary is stated for about 4,986 jobs and a currency for only 1,871. Cards show a stated salary with "(currency not stated)" when that is the case.
* **No "newest" claim or sort.** Dates exist only for LinkedIn postings.
* **Apply link only for real links.** Only LinkedIn rows carry one. `safe_url()` accepts only http(s), at most 2000 characters, no spaces or markup; `javascript:` and similar are never rendered (tested).
* **Placeholder employers are hidden.** 1,708 names of the form `Company-xxxxxx` were generated by the loader for postings with no employer; the UI shows no company instead (`ui.employer`).
* **Job areas are a title-keyword grouping**, and the page says "grouped by title"; "other" is not offered on Home.
* **Experience filter hides postings that state no experience**, and says so next to the control. LinkedIn experience is an approximation from seniority.
* **Example postings on Home are real postings** picked deterministically per day with a real company name and a city; the page says they are examples, "not the newest or the best". No testimonials, partner logos, user counts or match percentages exist anywhere.
* The index is described as a stored snapshot of public datasets, not a live job board.
* The neural "job function" panel was removed from the job page (the classifier is weaker than the bag-of-words baseline, `docs/DEEP_LEARNING.md`); its API endpoint remains.
* Collaborative filtering stays **off** in the UI until real interactions exist (no synthetic interactions presented as real).
* MyCareersFuture is not loaded, so it is not offered as a source.

**Added in Stage 2** (decisions the next stages must keep):

* **Only what the database can hold is offered on Profile.** `UserProfile` has no certification, multi-location or employment-type columns, so those fields are not shown and the page says so under "Not stored yet". **Job-area preferences are not stored in `preferred_categories`**: that column holds the EMSCAD `Job.category` labels (only about 12,000 postings have one), a different vocabulary from the title-keyword job areas used on Home and Find Jobs. Adding any of these needs a schema change and the user's approval.
* **Unknown skill names are never stored.** They are listed after saving ("not recognised as skills"), so the profile contains only skills Jobintel can match against postings. A skill that came from a resume keeps its source until the user removes it.
* **The checklist is not a score** (no percentage, no "profile strength"). The "Resume analysed" step stays open until the Resume page exists.
* **"Applied" is the user's own mark.** No status pipeline, no "interview" or "offer" states: nothing in the data could set them truthfully.
* **Password change ends the other browsers' sessions.** Sessions are signed cookies with no server-side list, so each carries `pwv`, the first 20 characters of a SHA-256 of the stored password hash; `load_current_user` compares it and logs the browser out when it differs. The browser that changed the password gets a fresh stamp and stays logged in. Cookies that predate the stamp count as logged out. The page states this in one sentence.
* **Deleting an account** removes, by explicit statements and not by relying on `ON DELETE CASCADE`: search result rows, searches, recommendations, skill-gap rows, job interactions (viewed / saved / applied), the user's skills, the profile (which holds any stored resume text) and the user. Job postings, companies and the skill table are untouched. The user must give the current password and tick a box; wrong passwords count against the same login throttle (tested).
* **Download my data** returns JSON with the account (user name, e-mail, created), the profile (including the saved resume text and file name, if any), skills with their source (manual / resume), every job interaction (viewed, opened from a search, saved, applied, last activity; jobs by id and title), and the search history, for that user only (tested not to contain another user's data), without the password hash. **Known gap for Stage 3: it does not yet include stored recommendation or skill-gap rows**, because nothing writes them yet; the export, the Account page wording ("Everything stored about you") and the delete list must be re-checked together when Stage 3 starts storing them.
* **No e-mail change and no e-mail password reset**: nothing sends e-mail. The Account page says so.

## 5. Run it

```powershell
# one-time (Windows PowerShell, project folder)
pip install -r requirements.txt
python scripts/build_index.py --write-db        # only if data/index/job_index.pkl does not exist yet
$env:SECRET_KEY = "put-a-long-random-string-here"   # without it, logins end whenever the server restarts
python scripts/run_web.py                       # http://127.0.0.1:5000
```

`scripts/run_web.py` uses Flask's built-in server: **local use only**. Settings (`jobintel/web/settings.py`): `SECRET_KEY`, `JOBINTEL_DEBUG`, `JOBINTEL_WARMUP`, `JOBINTEL_PARTS`, `JOBINTEL_LOG_SEARCHES`, `JOBINTEL_OPEN_REGISTRATION`, `MAX_UPLOAD_MB`, plus the `DB_*` variables. Searches are stored in the `searches` tables unless `JOBINTEL_LOG_SEARCHES=0` (page 1 of a default-sorted search only; anonymous searches are not linked to any user).
